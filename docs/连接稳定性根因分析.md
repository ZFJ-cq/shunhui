# 连接稳定性根因分析与修复记录

本文档是对当前实现的审查记录，不是运行指令。结论分为代码已证实、部署条件和仍需生产数据验证三类。

## 结论

当前实现已经覆盖会议的 SFU 转发、25 路媒体轨限制、动态视频层选择、STUN/TURN 参数下发、断流清理和自动重连。已确认的连接风险主要集中在会话替换和可观测性：旧页面被新连接替换时，旧页面原先会把断开当成普通离会并调用 `/leave`，可能误删新页面的参会状态；远端 Consumer 被信令关闭时，视频恢复定时器也缺少显式清理。

本次修复为旧 socket 增加 `session_replaced` 事件。旧页面收到该事件后只清理本地媒体并结束自身会话，不再调用 `/leave`；新页面继续使用同一参会席位。服务端同时记录连接、替换和断开原因。Consumer 关闭路径现在会显式停止视频恢复定时器。

## 已确认的问题与修复

### 会话替换误删参会状态（已修复）

服务端为同用户新连接保留“单会话”语义，会关闭旧 socket 并清理旧 SFU peer。旧客户端现在收到明确的 `session_replaced` 事件，`MeetingView` 通过 `skipLeave` 跳过 API 离会，避免旧页面把新页面的参会席位删除。真正的主持人移出、会议结束和用户主动离会仍按原流程处理。

### Consumer 视频恢复定时器清理（已修复）

每个视频 Consumer 的恢复 interval 现在登记到清理表；收到 `consumer_closed` 或 `producer_closed` 时先清除 interval，再关闭 Consumer 和远端媒体对象。

### 服务端连接生命周期日志（已补充）

服务端记录 meeting、user、socket、替换数量和 Socket.IO disconnect reason，不记录 token、SDP、ICE 凭证或聊天内容。生产环境应集中收集这些日志，以统计重连成功率、`ping timeout`、`transport close` 和会话替换次数。

## 不能仅凭文档确认的假设

- `waitForTransport` 的 10 秒超时是否过短，取决于实际网络、TURN 中继和浏览器 ICE 收集耗时。当前代码会对媒体失败进行一次自动重建，不能据此断言它是“十几秒整场断开”的根因。
- ICE 是否可达不能笼统判定为失败。跨设备部署必须让 `RTC_ANNOUNCED_IP` 对客户端可达，开放 mediasoup RTP 端口，并配置可用 TURN；localhost 配置只适合同机开发。
- Socket.IO 默认心跳为 25 秒间隔、20 秒超时；当前 Nginx `proxy_read_timeout` 为 75 秒，静态配置没有发现小于心跳周期的代理超时。若线上网关不同，应确认其空闲超时大于心跳周期。
- “约十几秒断开”仍需结合客户端 `disconnect` reason、重连序列、媒体 transport 状态、服务端日志和 `webrtc-internals` 才能定因。不能把会话替换竞态、ICE 不可达或媒体超时中的任何一项直接当作已证实根因。

## 部署核对

生产或跨网环境至少检查：

1. `RTC_ANNOUNCED_IP` 是浏览器可达的公网或内网地址，不使用 `127.0.0.1`。
2. `TURN_URLS`、`TURN_SECRET`、Coturn `external-ip` 和 UDP/TCP 端口一致。
3. `RTC_MIN_PORT`–`RTC_MAX_PORT` 在防火墙和云安全组放行。
4. `APP_ORIGIN` 与实际 HTTPS 前端源一致；反向代理转发 `/socket.io/` 的 Upgrade，并保持超时大于 Socket.IO 心跳周期。
5. 本地开发使用可信证书（例如 mkcert）访问 `https://localhost`，否则浏览器会阻止摄像头、麦克风和屏幕共享。

## 验证

应运行 `npm run build`、`npm test`；具备 mediasoup 运行环境时再运行 `REAL_SFU=1 npm test`。集成测试覆盖断线后席位保留、同用户新会话替换以及媒体传输重新创建。跨网 TURN 和真实浏览器媒体质量仍需在目标网络实测。
